# What this app actually does — in plain English

Written so you can say it in your own words to a judge in 3–5 minutes, without
claiming anything the demo doesn't actually do.

---

## 1. The one-sentence version

**When an AI agent makes a decision about data, this records an unforgeable
receipt of every step it took to get there — and the receipt is written by the
laptop, not by the model.**

---

## 2. What a "shard" is here

In federated learning, no single party holds the whole dataset. Each
participating site — a hospital, a bank, a phone — holds its own slice of it.
That slice is a **shard**. A training round works by every site training on its
own shard and only the model updates being combined centrally. The raw shard
never moves.

**Be honest about the demo:** there is no real CIFAR-10 data in this run. A
shard is represented by a one-line **manifest** — a short string that describes
it:

```
shard-a:1024rows:cifar10
```

That reads as: the shard labelled `shard-a`, holding 1024 rows, of CIFAR-10.
In a real deployment the manifest would be generated by the site from its
actual data. Here we type it in. Say that out loud if asked — it's a harness,
not a trained federation.

---

## 3. What gets attested, and by whom

The agent has exactly one tool, `attest_artifact`. Given a shard's manifest, it
returns:

- a **SHA-256 digest** of the manifest string,
- its **byte length**,
- the **ledger sequence number** the attestation was written to.

The critical detail, and the thing worth 30 seconds of your pitch:

> **The model does not compute the hash. The laptop does.**

The language model is only allowed to *decide* that a shard needs attesting and
*which* shard. The moment it asks for a fingerprint, execution leaves the model
entirely: `attest_artifact` runs as ordinary Python inside the AgentApp process
on your machine, and the digest it returns is handed back to the model as a
fact it cannot argue with.

This matters because a model asked to "hash this" will happily emit
sixty-four plausible hex characters that are not the hash of anything. The
instructions tell it *never invent a hash yourself*, but instructions are not a
guarantee — moving the computation out of the model is. **The model is treated
as an untrusted planner, not as a source of truth.**

---

## 4. The ledger — why it can't be quietly rewritten

Every step of the run is appended to a ledger: the run starting, each request
sent to the model, each response that came back, each tool call and its result,
the run finishing.

Each entry carries a hash that covers **both its own contents and the previous
entry's hash**:

```
chain[n] = sha256( chain[n-1] + entry[n] )
```

That's the whole trick, and it's worth drawing on a whiteboard. Because entry 5
locks in entry 4's hash, which locks in entry 3's, going back and editing entry
2 — say, to hide that the agent looked at a shard it shouldn't have — changes
entry 2's hash, which breaks entry 3's, and every hash after it. You cannot
edit the middle of the record without visibly destroying the end of it.

The final line of the run prints the **ledger head** — one 64-character hash
that stands for the entire run. Two runs that did the same things produce the
same intermediate digests; a run that did something different doesn't.

The run also prints `chain integrity: VERIFIED`, which is the app recomputing
the whole chain from scratch and confirming it matches.

---

## 5. What crossed the network and what didn't

This is the question a good judge will ask, so be precise. In the demo you ran:

| Component | Where it ran |
| --- | --- |
| Flower SuperLink | your laptop |
| The AgentApp (the agent loop) | your laptop |
| `attest_artifact` — the hashing | **your laptop** |
| The ledger | **your laptop, in memory and stdout** |
| The language model (Qwen3.5-397B on vLLM) | a remote GPU host |

**Left the machine:** the prompt text going to the model — which includes the
manifest strings, because we put them in the prompt — and the model's replies
coming back.

**Never left the machine:** the hashing, the ledger, and the integrity check.
No digest was ever taken on trust from a remote party.

**Do not say "no data left the laptop."** In this run the manifests did go to
the model host. The accurate sentence is:

> "The shard contents never move — only a fingerprint does. Today the manifests
> themselves still go to the model as part of the prompt; in a real deployment
> the manifest is generated site-side and only the digest crosses the wire."

That's the honest architecture claim, and it's still a strong one.

---

## 6. What made run 2 refuse — and what that does and doesn't prove

Run 1 was given two shards, `shard-a` and `shard-b`, attested both, and
concluded the round was reproducible.

Run 2 was given **one** shard, `shard-c`, and asked the same question. It
attested the shard correctly — and then declined to answer:

> "I cannot determine if the round is reproducible based on this single shard
> alone, as reproducibility requires all participating sites' shards to be
> attested. Please provide the manifests for all other contributing sites."

That is the demo beat: the agent completed the work it could actually justify
and **stopped short of the claim it couldn't**, asking for the missing inputs
instead of guessing.

**Now the honest part, and you should volunteer it rather than be caught by
it.** That refusal is the *model's own judgment*. It is not an enforced policy.
There is no rule in the code that says "refuse unless N sites have reported."
A different model, or the same model on a different day, might have answered
"yes, reproducible" — and the ledger would have faithfully recorded it doing
so.

So the correct framing is:

> "The ledger doesn't stop the agent from being wrong. It makes it impossible
> for the agent to be wrong *quietly*. Every input that led to that judgment is
> fingerprinted in the record — so when someone asks six months later why this
> round was signed off, the answer is in the chain, not in someone's memory."

If you want that refusal to be a *guarantee* rather than a *tendency*, the fix
is a quorum check in the harness that refuses to emit `run.completed` until N
distinct shards carry attestations. That's the obvious next commit, and saying
so is a better answer than pretending it's already there.

---

## 7. The bit that makes the ledger interesting rather than decorative

The vLLM server hosting the model was started without a tool-call parser. So
when the model decided to call `attest_artifact`, the server didn't return a
structured tool call — it returned the model's raw request as plain assistant
text:

```
<tool_call><function=attest_artifact><parameter=name>shard-a</parameter>...
```

The harness recovers those, runs the tool, and carries on — but it also writes
a `provider.unparsed_tool_calls` entry into the ledger saying it had to.

That's the point of the whole thing in miniature: **the run degraded, it still
worked, and the record says it degraded.** A provenance system that only logs
the happy path is worthless. Judges who have operated real systems will
recognise that instantly, so don't hide it — lead with it.

---

## 8. Honest limitations (pick one for your 15-second limitation slot)

- **The ledger is not anchored anywhere.** It's tamper-evident against someone
  editing the record after the fact, but the process that *wrote* it could have
  written a different one from the start. Nobody countersigns it. Real
  provenance needs an external witness — a second node, or a signature.
- **The refusal in run 2 is a model tendency, not an enforced rule** (see §6).
- **A shard is a hand-typed string, not real data.** No training happens here.
- **One tool, one node.** The federation is not exercised; this runs on a local
  SuperLink, not across SuperNodes.
